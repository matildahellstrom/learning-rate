# Solving the wrong problem 🧭

Imagine asking a coding agent: _"add Google sign-in"_. Twenty minutes later it proudly shows you a new login system, built from scratch, next to the one your app already had. The code is tidy. It even runs. It's just not what you needed. (A made-up story, but Anthropic's guide warns that letting Claude "jump straight to coding can produce code that solves the wrong problem".)

The fix isn't a cleverer prompt. It's a workflow that puts the right checks in the right order: **explore**, **plan**, **implement**, **verify**.

This lesson walks through each step, what kind of mistake each one catches, and when to skip the plan altogether.

---

## The loop under the hood

Claude Code's docs describe its work as an **agentic loop** with three phases: "gather context, take action, and verify results". They add that the phases "blend together": a question about your code might only need the first, while "a bug fix cycles through all three phases repeatedly".

The four-step workflow is a way of steering that loop on purpose. **Explore** and **plan** are gathering context. **Implement** is taking action. **Verify** closes the loop.

A note on names: Anthropic's best-practices guide lists the steps as explore, plan, implement and **commit**, and puts "give Claude a way to verify its work" first among its tips. This lesson folds verification into the workflow, because it's the step that decides whether you can trust the rest.

---

## Explore: look before you touch

In the first step the agent reads, searches and asks, but doesn't change anything.

As of October 2026, Claude Code has a **plan mode** for this. Its docs say Claude "reads files, runs shell commands to explore, and writes a plan, but does not edit your source", and edits stay blocked until you approve the plan (except in interactive terminal sessions where bypassing permissions is available). You enter it with `Shift+Tab`, by starting a prompt with `/plan`, or with `claude --permission-mode plan`.

The guide's example of an exploring prompt:

> _read /src/auth and understand how we handle sessions and login. also look at how we manage environment variables for secrets._

Notice how scoped it is: one folder, two questions. The context management lesson showed why: an unscoped "investigate" can read hundreds of files. For bigger searches, a subagent can explore in its own window and return a summary.

---

## Plan: agree on the change before it exists

Next, ask for a plan. The guide's example: _"I want to add Google OAuth. What files need to change? What's the session flow? Create a plan."_

A plan is cheap to change. Moving a line in a plan takes seconds; unpicking the same mistake from a dozen edited files takes much longer. As of October 2026, Claude Code lets you open the plan in your editor with `Ctrl+G` and change it directly, and when it's ready you choose to approve it or keep planning.

For a larger feature, the guide suggests going one step further: have Claude **interview you** about edge cases and trade-offs and write a spec file, then start a **fresh session** to build it. The new session gets clean context and a written spec. The guide says the most useful specs "name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step".

---

## When to skip the plan

Planning isn't free. The guide says plan mode "also adds overhead".

🤔 Predict: which of these deserve a plan? (a) fix a typo in an error message, (b) rename a variable, (c) move an app from one payment provider to another.

Only (c). The guide's rule of thumb: "If you could describe the diff in one sentence, skip the plan." It says planning is most useful when:

- you're **uncertain about the approach**,
- the change **modifies several files**, or
- you're **unfamiliar with the code**.

For (a) and (b), just ask for the change. The guide is honest that its advice is a starting point: "Sometimes you should skip planning and let Claude figure it out because the task is exploratory."

---

## Implement: small steps, from the plan

Now the agent writes code. The guide's example prompt ties it back to the plan and to a check:

> _implement the OAuth flow from your plan. write tests for the callback handler, run the test suite and fix any failures._

Size matters here too. In Anthropic's experiments with long-running agents, in which an agent built a clone of the claude.ai web app over many sessions, the first of two failure patterns was that the agent tended to try "to do too much at once". Often its context ran out mid-feature, and the next session had to guess what had happened. Asking it to work on **one feature at a time** turned out to be, in the author's words, "critical". The agent was also asked to commit its progress to git with descriptive messages and to summarise it in a progress file, so a bad change could be reverted and the next session could see what was done.

---

## Verify: a check the agent can run

Here's the step that's easiest to skip. Anthropic's guide explains why it matters: "Claude stops when the work looks done." Without a check, "looks done" is the only signal, and you become the one catching every mistake.

A check is anything that returns a result the agent can read: a test suite, a build's exit code, a linter, a script comparing output to a known answer, or a screenshot compared with a design.

🤔 Predict: why not just tell the model, "now double-check your work"?

Because rereading its own answer gives it no outside information. Huang and colleagues (2023) studied **intrinsic self-correction**, where a model tries to fix its answer "based solely on its inherent capabilities, without the crutch of external feedback". On reasoning tasks, they found models struggled to self-correct that way, and "at times, their performance even degrades". A failing test is different: it's **external feedback** the model didn't produce.

The guide adds one more habit: have the agent **show evidence**, such as the test output or the command it ran and what came back, rather than just saying it's done.

---

## Test like a user

Passing tests can still miss the point. In the long-running agent experiments, the agent would write unit tests or try the server with `curl`, yet "fail [to] recognize that the feature didn't work end-to-end".

What helped: giving it browser automation tools and asking it to test "as a human user would". The author says this "dramatically improved performance", because the agent could find bugs that weren't obvious from the code. It wasn't perfect: the agent couldn't see the browser's own pop-up alerts, and features that used them tended to be buggier.

A second check is a **fresh pair of eyes**. The guide suggests a review in a fresh context, such as a subagent that sees only the diff and your criteria. It notes that in a fresh context Claude "won't be biased toward code it just wrote". It also warns that a reviewer asked to find gaps "will usually report some, even when the work is sound", so tell it to flag only what affects correctness or the stated requirements.

## Your turn: split a request

Here's a vague request:

> _make the API stop people spamming it_

Before reading on, sketch what you'd ask for at each step: explore, plan, implement, verify.

One good version (yours can differ):

1. **Explore** (plan mode): _"read src/middleware and tell me how requests are handled today, and whether we have any rate-limiting code already."_
2. **Plan**: _"plan a per-user rate limiter: which files change, where the limits are stored, what users see when they hit the limit."_ Read the plan and edit it.
3. **Implement**: _"implement the plan. add tests for a user under the limit, at the limit, and over it."_
4. **Verify**: _"run the test suite and show me the output"_, then perhaps a fresh subagent reviewing the diff against the plan.

Each step has its own job. Exploring finds the existing code, planning catches the wrong design, and the tests catch the wrong behaviour.

## Common misconceptions

- **"Planning is always worth it."** It adds overhead. If the diff fits in one sentence, ask for it directly.
- **"If the agent says it's done, it's done."** It stops when the work looks done. Ask for evidence from a check it ran.
- **"Asking the model to double-check is verification."** Without outside feedback, self-correction is unreliable on reasoning tasks, and can make things worse.
- **"Passing unit tests means the feature works."** Tests check only what they test. In Anthropic's experiments, end-to-end testing in a browser caught broken features that the agent's unit tests and curl checks had missed.
- **"A reviewer's findings are all must-fixes."** A reviewer asked for gaps will usually find some. Scope it to correctness and requirements.

## What you learned

- Claude Code works in an **agentic loop**: gather context, take action, verify results.
- **Explore** first: read and ask without editing, for example in **plan mode**.
- **Plan** when the approach is uncertain, the change spans files, or the code is new to you; skip it for one-sentence diffs.
- **Implement** in small steps from the plan, committing as you go.
- **Verify** with a check the agent can run, because it stops when work _looks_ done and self-correction without feedback is unreliable.
- Test **end to end** where you can, and use a **fresh reviewer** scoped to what matters.
