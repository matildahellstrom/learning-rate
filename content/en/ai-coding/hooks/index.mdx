# The rule that slipped 🪝

Your CLAUDE.md says, in capitals, **IMPORTANT: run the formatter after every edit.** For the first dozen edits Claude does. On the thirteenth, deep in a tricky refactor, it doesn't, and the pull request fails its style check.

Nobody did anything wrong. The CLAUDE.md lesson showed that instruction files are advice: Claude tries to follow them, with no guarantee. Anthropic's best-practices page puts it this way: CLAUDE.md instructions are "advisory", while hooks "are deterministic and guarantee the action happens."

A **hook** is a command that Claude Code itself runs at a fixed moment, such as after every file edit. This lesson covers how hooks are set up, how they can block an action, the surprises in how they work, and how to keep them safe.

---

## Code that runs, not advice that's read

As of October 2026, Claude Code's docs describe hooks as "user-defined shell commands" that run "at specific points in its lifecycle, which gives you deterministic control: certain actions always happen rather than relying on the LLM to choose to run them."

That is the whole difference from CLAUDE.md and skills. Those are text Claude reads and interprets. Claude doesn't decide whether a hook runs: Claude Code runs it when its event happens, and the docs say it "fires on its event without Claude deciding".

Besides shell commands, as of October 2026 a hook can also send an HTTP request, call a tool on an MCP server, ask a Claude model to judge, or start a subagent. Most hooks are plain commands, and that's what this lesson focuses on.

Hooks live in a `hooks` block in a settings file:

- **`~/.claude/settings.json`**: all your projects, on your machine only.
- **`.claude/settings.json`** in a repository: that project, and it can be committed for the team.
- **`.claude/settings.local.json`**: that project, just for you.

Run `/hooks` to see what's configured. And you don't have to write the JSON by hand: Anthropic's best-practices page suggests asking Claude, for example _"Write a hook that runs eslint after every file edit."_

---

## When hooks fire

Each hook is attached to an **event**, a moment in Claude Code's loop. As of October 2026, the docs list 33 of them. A handful cover most uses:

- **`SessionStart`**: a session begins or resumes.
- **`UserPromptSubmit`**: a prompt is submitted (by you, or a turn Claude Code starts itself), before Claude processes it.
- **`PreToolUse`**: before a tool call runs. It **can block** the call.
- **`PostToolUse`**: after a tool call succeeds.
- **`Notification`**: Claude Code sends a notification, for example when it needs your input.
- **`Stop`**: Claude finishes responding.
- **`SubagentStop`**: a subagent finishes.
- **`PreCompact`**: just before the conversation is compacted.

The guide's own examples show the range: a desktop alert when Claude is waiting for you, formatting every edited file, blocking edits to protected files, and putting key context back after compaction.

## Anatomy of a hook

Here's the docs' example that runs Prettier, a code formatter, after every edit:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write"
          }
        ]
      }
    ]
  }
}
```

Three parts: the **event** (`PostToolUse`), a **matcher** that narrows it to the `Edit` and `Write` tools, and the **command**. When the hook fires, Claude Code sends details of the event to the command's standard input as JSON, including the tool's name and its arguments. Here `jq` pulls out the edited file's path and hands it to Prettier.

As of October 2026, the docs say that without a matcher, "a hook fires on every occurrence of its event."

🤔 Predict: Claude changes a file by running a `sed` command through the Bash tool. Does this formatter run?

**No.** The matcher names tools, and Bash isn't `Edit` or `Write`. The docs warn that "Claude can also create or modify files by running shell commands." If a hook must see every change, they suggest also matching `Bash|PowerShell` and listing changed files, adding a `Stop` hook that scans the working tree once per turn, or using a `FileChanged` hook.

## Saying no: exit code 2

A `PreToolUse` hook can stop a tool call before it happens. As of October 2026, the docs' script for protecting files works like this: read the JSON, check the file path against a list such as `.env` and `.git/`, and if it matches, print a reason to standard error and **exit with code 2**.

Claude Code then blocks the edit and passes the reason to Claude, which the docs say lets it "adjust its approach".

🤔 Predict: your script exits with code 1 instead, the usual Unix code for "something failed". Is the edit blocked?

**No.** As of October 2026, the exit codes mean:

- **0**: no objection. For `PreToolUse` this "doesn't approve the tool call": your normal permission rules still apply.
- **2**: block the action, with standard error as the reason. Some events, such as `SessionStart`, can't be blocked; there, exit 2 shows you the message and carries on.
- **Anything else**: for most events, a **non-blocking error**. You see a notice, and the action goes ahead (unless the hook prints valid JSON, which then decides, or is set to block on failure).

The reference spells it out: by default, exit 1 without valid JSON output is a non-blocking error, "even though 1 is the conventional Unix failure code. If your hook is meant to enforce a policy, use `exit 2`."

<Deeper title="Go deeper: JSON decisions">
Instead of relying on exit codes, a hook can print a JSON object to standard output to make a finer decision. A `PreToolUse` hook, for example, can return a permission decision of `allow`, `deny`, `ask` or `defer`.

As of October 2026, when several hooks match the same event, Claude Code runs them all in parallel and waits for every one to finish before combining the answers. For `PreToolUse` decisions, "the most restrictive answer applies", in the order deny, defer, ask, allow. One hook's deny doesn't stop a sibling hook from running, so the docs warn against relying on it to prevent another hook's side effects.

</Deeper>

## Stronger than permission modes

Claude Code has permission modes, including one that skips its usual approval prompts. Where do hooks sit?

As of October 2026, the docs say `PreToolUse` hooks "fire before any permission-mode check", so a hook that denies a call "blocks the tool even in `bypassPermissions` mode". The docs say this lets you enforce policy that users "can't bypass by changing their permission mode". (One caveat in the docs: an installed mod can still approve a call your hook blocked, unless the hook is in managed settings.)

It only works one way, though. Hooks in settings files "can tighten restrictions but not loosen them past what permission rules allow": a hook that says "allow" doesn't override a deny rule.

The features overview sums up where rules belong: "An instruction like 'never edit `.env`' in CLAUDE.md or a skill is a request, not a guarantee. A `PreToolUse` hook that blocks the edit is enforcement."

## A gate before "done"

A `Stop` hook runs when Claude finishes responding. As of October 2026, Anthropic's best-practices page describes it as "a deterministic gate": it "runs your check as a script and blocks the turn from ending until it passes." If the tests fail, the hook blocks and Claude keeps working instead of stopping.

Two cautions from the docs:

- `Stop` fires "whenever Claude finishes responding, not only at task completion".
- A blocking hook can loop. Its input has a `stop_hook_active` field, which is true when Claude is already continuing because of a Stop hook, so your script can let it stop. As a backstop, Claude Code overrides a Stop hook after it blocks **eight times in a row** with no tool call in between.

Some checks need judgement rather than a script. For those, as of October 2026, a hook can be `"type": "prompt"`, which sends the event to a Claude model that answers with an OK or a reason. An `"agent"` type can also inspect files and run commands, but the docs mark it as experimental.

---

## What hooks can't do

Hooks are powerful but narrow. As of October 2026, the docs list some limits:

- **`PostToolUse` can't undo anything**: "the tool has already executed". To prevent an action, use `PreToolUse`.
- **Command hooks can't run `/` commands or tool calls.** They talk to Claude Code only through output and exit codes.
- **Text they return lands in context.** A hook costs no context unless it returns output, which Claude Code adds to the conversation for Claude to read.

That last point is useful: a `PostToolUse` linter hook can feed its warnings straight back to Claude. And it's why the features overview suggests hooks for things that "must happen the same way every time" and don't need Claude to think, and a skill when Claude should decide how to apply the steps.

---

## A hook runs as you

The flip side of "runs whatever Claude decides" is that a hook runs whatever is in the file. As of October 2026, the reference warns: "Command hooks execute shell commands with your full user permissions. They can modify, delete, or access any files your user account can access."

That matters most for hooks that arrive with a repository. In an interactive session, Claude Code holds back hooks until you accept the folder's **workspace trust** prompt. But the docs note that in a scripted `claude -p` run, the folder is treated as trusted, "so hooks committed in a repository's `.claude/settings.json` run in a folder you've never trusted". Before scripting Claude Code over someone else's repository, read its `.claude/` settings first.

The reference's advice for writing hooks includes: validate the input rather than trusting it, always quote shell variables (`"$VAR"`, not `$VAR`), check paths for `..`, use absolute paths for scripts, and stay away from sensitive files such as `.env` and keys.

## Common misconceptions

- **"A hook is a stronger kind of instruction."** It isn't an instruction at all: Claude Code runs it, and Claude doesn't decide whether it runs.
- **"Exit 1 blocks the action."** Only exit 2 blocks; other non-zero codes are non-blocking errors by default.
- **"A PostToolUse hook can catch and reverse a bad edit."** The tool has already run; block it in `PreToolUse` instead.
- **"An Edit|Write matcher sees every file change."** Shell commands can change files too; match `Bash|PowerShell` as well, or check the working tree.
- **"Hooks are harmless config."** They run with your full user permissions, so review any hook before you let it run.

## What you learned

- A **hook** is a command Claude Code runs at a fixed **event**; CLAUDE.md and skills are advice, hooks are enforcement.
- Hooks live in **settings files**: personal, project or local.
- **`PreToolUse`** can block before an action; **`PostToolUse`** reacts after and can't undo.
- **Exit 2** blocks, with standard error as the reason; **exit 1** doesn't, by default.
- **Matchers** name tools, so a Bash command can slip past an `Edit|Write` hook.
- A **`Stop`** hook can gate "done" on passing checks; check `stop_hook_active` to avoid loops.
- Hooks run **with your permissions**: review them, especially in repositories you didn't write.
