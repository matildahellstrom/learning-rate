# The goldfish and the library 📜

You paste a 300-page report into a chatbot and ask about page 12. It answers. Then, after a long back-and-forth, it seems to forget something you said at the very start.

Both behaviours come from the same thing: the model's **context window**, the text it can see at one time. It isn't the model's knowledge (that's baked into its weights during training). It's closer to a desk: whatever is on the desk can be used, and the desk has a size.

This lesson covers what fills the window, how big windows are today, the **KV cache** that makes generating text fast but eats memory, the tricks that shrink it, and why a bigger window isn't automatically a better one.

---

## What's in the window

Anthropic's docs define the context window as all the text a model "can reference when generating a response, including the response itself", and call it the model's "working memory".

It's measured in **tokens** (the tokenisation lesson covers what those are), and in an API call, **everything** counts:

- the **system prompt** (the instructions set before the chat starts),
- every **message** so far, including documents, images and tool results,
- the **tool definitions**,
- and the **output** the model writes, including any thinking.

There's one more surprise. The model doesn't remember your last request between API calls. Each turn, the **whole conversation** is sent again, so the window fills up turn by turn.

🤔 Predict: a window holds 200,000 tokens, and each turn (your message plus the reply) adds 2,000. Roughly how many turns fit?

About **100**: 200,000 ÷ 2,000. Long documents or long thinking use the space much faster.

---

## How big is a window?

As of October 2026, Anthropic's docs list a **1-million-token** window for current models such as Claude Opus 5.5, with up to 128k tokens of output per request; other Claude models have 200k. Open models vary too: Meta's Llama 3 paper describes a window of up to 128K tokens.

What happens when the window is full? It depends on the software around the model:

- The Claude API returns an error ("prompt is too long") if the input alone is larger than the window.
- Chat apps such as claude.ai can manage the window on a "first in, first out" basis, dropping the **oldest** messages, which is one way a chatbot can "forget" the start of a conversation.
- **Compaction** summarises the earlier parts of a conversation, so it can continue past the limit; Anthropic offers this on the server, in beta as of October 2026.

---

## The repeated work problem

Remember from the next-token prediction lesson: a model writes **one token at a time**, and each new token is chosen by looking at everything before it. In the attention lesson, "looking" means comparing the new token's **query** with every earlier token's **key**, then mixing their **values**.

🤔 Predict: to pick token number 1,001, does the model need to recompute the keys and values of the first 1,000 tokens?

It **doesn't**. Thanks to the causal mask, a token only ever attends to tokens **before** it. So its keys and values, in every layer, depend only on the text up to that point. Adding new tokens later can't change them.

So the model computes each token's keys and values **once** and keeps them. That store is the **KV cache** (K for keys, V for values). Each new token adds one more entry, and only that entry needs computing.

---

## Two phases: prompt, then generation

The KV cache splits generation into two phases, as Kwon and colleagues describe in their 2023 PagedAttention paper:

- **The prompt phase** (often called **prefill**): the whole prompt is known up front, so the model processes all of its tokens in parallel, filling the cache. GPUs are good at this.
- **The generation phase** (often called **decode**): new tokens come one at a time, each reading the whole cache and adding its own keys and values. Each step depends on the last, so this part can't be parallelised the same way.

That's one reason a long prompt can add a pause before the first word appears. After that the rest streams out word by word, and for most requests this one-at-a-time phase takes most of the time.

<Deeper title="Go deeper: what the cache saves">
Without a cache, writing token $t$ means rerunning the network on all $t$ tokens so far. With a cache, the new token is the only one pushed through the layers, and its attention reads $t - 1$ stored keys and values.

Attention still grows with length: the new token's query is scored against every cached key, so each step costs work proportional to $t$. Generating $n$ tokens that way adds up to about

$$
1 + 2 + \dots + n = \frac{n(n+1)}{2}
$$

query-key scores per head, per layer: the square-of-the-length growth from the attention lesson. The cache doesn't remove that; it removes the repeated work of recomputing every earlier token's keys and values.

</Deeper>

## The memory bill

Caching isn't free. Each token's entry holds a key vector **and** a value vector, in **every layer**.

The PagedAttention paper works it out for a 13-billion-parameter model called OPT. Its vectors have 5,120 numbers, it has 40 layers, and each number takes 2 bytes:

**2 (key and value) × 5,120 × 40 × 2 bytes ≈ 800 KB per token**

At OPT's maximum of 2,048 tokens, that's about **1.6 GB** for a single request, on graphics cards that held tens of gigabytes. Serve many users at once and the cache, not the model, can become what limits you.

<Deeper title="Go deeper: the KV cache formula">
For one token, with $L$ layers, $h_{kv}$ key-value heads per layer, $d_h$ numbers per head and $b$ bytes per number:

$$
\begin{aligned}
\text{bytes per token} &= 2 \cdot L \cdot h_{kv} \cdot d_h \cdot b \\
\text{cache} &= \text{bytes per token} \\
&\quad \times \text{tokens} \times \text{requests}
\end{aligned}
$$

For OPT-13B, $h_{kv} \cdot d_h = 5{,}120$ (the full vector width), $L = 40$ and $b = 2$, giving 819,200 bytes. The paper rounds that to 800 KB, which is exact if 1 KB means 1,024 bytes. Storing the cache in fewer bits shrinks $b$ (the quantisation lesson covers that).

</Deeper>

## Sharing keys and values

In ordinary multi-head attention, every head has its own keys and values, so every head adds to the cache.

Shazeer (2019) proposed **multi-query attention**: keep many query heads, but let all of them **share one** set of keys and values. The cache shrinks by the number of heads, and he found decoding got much faster with only a minor drop in quality.

Ainslie and colleagues (2023) noted that multi-query attention can cost quality, and proposed a middle ground, **grouped-query attention (GQA)**: a few key-value heads, each shared by a group of query heads. In their tests it came close to full multi-head quality at speeds comparable to multi-query.

Meta's Llama 3 uses GQA "to reduce the size of key-value caches during decoding". Its 8-billion-parameter model has 32 layers and 32 query heads of 128 numbers each, but only **8** key-value heads.

🤔 Predict: how much smaller is its cache than if all 32 heads kept their own keys and values?

**4 times** (32 ÷ 8). Per token, that's 2 × 32 × 8 × 128 × 2 bytes = 131,072 bytes, or 128 KB. A full 128K-token window still needs about **16 GB** of cache for one request, which is why long contexts are costly to serve.

---

## Wasted memory

There's another catch. Before a model starts writing, nobody knows how long the answer will be. Kwon and colleagues found that serving systems of the time reserved memory for each request in advance, often sized for the longest possible sequence. In their tests of three versions of one such system (Orca, which they rebuilt themselves), only **20.4% to 38.2%** of the KV cache memory actually held token data, even in a version told each answer's length in advance; the rest sat in reserved slots or was lost to fragmentation.

Their fix, **PagedAttention**, borrows an old idea from operating systems: **virtual memory paging**. Instead of one big reserved block per request, the cache is stored in small fixed-size blocks handed out as needed, which don't have to sit next to each other. Their serving system, vLLM, got close to zero waste and, in their tests, improved throughput 2 to 4 times over systems such as FasterTransformer and Orca, at the same latency.

---

## A bigger window isn't a better memory

Fitting text in the window doesn't mean the model uses all of it equally well.

Liu and colleagues (2023) gave models several documents and a question whose answer was in just one of them, then moved that document around. Performance often traced a **U shape**: best when the relevant document came first or last, worst in the middle, even for models built for long contexts. In one case, GPT-3.5-Turbo with the answer in the middle did **worse** than with no documents at all (56.1%).

A 2025 report from Chroma, by Hong, Troynikov and Huber, tested 18 models on deliberately simple tasks, changing only the length of the input. Performance grew less reliable as inputs got longer, often in uneven and surprising ways. The report calls this **context rot**; Anthropic's docs use the same term and draw the practical lesson: curating what's in context matters as much as how much space there is.

---

## Common misconceptions

- **"The context window is what the model knows."** Knowledge lives in the weights from training. The window is the working space for this one request.
- **"The model remembers the conversation on its own."** Each turn, the whole conversation is sent again. Drop it and the model has no idea what came before.
- **"The KV cache stores the model's answers."** It stores keys and values, the intermediate vectors attention needs, so they aren't recomputed.
- **"If it fits, the model will use it."** Studies of long inputs find models use some positions and lengths much less reliably than others.
- **"Cached prompts don't count towards the window."** Anthropic's docs say cached prefixes still occupy it; caching changes what you pay, not the space used.

## What you learned

- The **context window** is everything the model can see while writing, measured in **tokens**, and it includes its own **output**.
- As of October 2026, current Claude models have **1M-token** windows; the whole conversation is resent every turn.
- The **KV cache** keeps each token's keys and values so they're computed once: a parallel **prompt phase**, then one-at-a-time **generation**.
- The cache costs memory: **2 × layers × KV heads × head size × bytes** per token.
- **Multi-query** and **grouped-query attention** share keys and values to shrink it; **PagedAttention** stops it being wasted.
- Long contexts are used unevenly: **lost in the middle** and **context rot**.
