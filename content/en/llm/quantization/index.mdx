# Squeezing a giant into a backpack 🎒

A large language model is a huge pile of numbers. A model with 70 billion weights, each stored as a 16-bit number, needs about **140 GB** just for the weights. That's far more memory than a laptop or a single typical GPU has.

What if each number used only **4 bits**? Then the same model needs about **35 GB**.

That's **quantisation**: storing numbers more coarsely, like rounding prices to the nearest euro. You lose a little precision and gain a lot of room.

---

## Numbers have sizes

Every weight is stored with some number of **bits**. Common choices:

- **32-bit float** (FP32): 4 bytes. The classic for training.
- **16-bit float** (FP16 or BF16): 2 bytes. The usual way to ship a model.
- **8-bit** (INT8 or FP8): 1 byte.
- **4-bit** (INT4, FP4 and friends): half a byte.

Memory for the weights is simply **number of weights × bytes per weight**. For a 7-billion-weight model: 28 GB at 32 bits, 14 GB at 16 bits, 7 GB at 8 bits and 3.5 GB at 4 bits.

🤔 Quick check: how big is that 70-billion-weight model at 8 bits? (70 GB.)

The running model also needs memory for other things, like the KV cache (the context windows lesson covers this), so treat these as the floor, not the total.

---

## Smaller is faster, too

When a model generates text, each new token needs **every weight** to be streamed from memory into the compute units. For big models that data movement, not the arithmetic, is usually the bottleneck. (The speculative decoding lesson has another trick built on the same fact.)

So fewer bytes per weight means less to move, and more tokens per second. The GPTQ paper, for example, measured end-to-end speed-ups of about 3.25× over 16-bit on NVIDIA A100 GPUs for its quantised models.

Quantisation also lets you use cheaper hardware, or serve more users on the same machine.

---

## Rounding onto a grid

How do you turn a weight like 0.5 into a tiny integer? Pick a **scale** $s$ and round:

**stored integer = round(weight ÷ scale)** · **weight ≈ stored integer × scale**

Take four weights: **0.5, −1.27, 0.03, 0.9**. The largest size is 1.27.

**8-bit** (integers −127 to 127): scale = 1.27 ÷ 127 = 0.01. The stored integers are 50, −127, 3, 90. Multiply back by 0.01 and every weight comes back exactly. Lucky!

**4-bit** (integers −7 to 7): scale = 1.27 ÷ 7 ≈ 0.181. Now 0.5 ÷ 0.181 ≈ 2.76 rounds to **3**, which reads back as 0.544. The 0.9 becomes 5 → 0.907, and the 0.03 rounds to **0**.

Each weight moves by at most half a grid step. With fewer bits the grid is coarser, so the errors grow.

<Deeper title="Go deeper: scales, zero points and the error bound">
With $b$ bits, **symmetric** quantisation uses integers $-(2^{b-1}-1), \dots, 2^{b-1}-1$ and a scale $s = \max_i |w_i| / (2^{b-1} - 1)$:

$$
\begin{gathered}
q_i = \operatorname{round}\!\left(\frac{w_i}{s}\right), \qquad \hat w_i = s\, q_i \\
|w_i - \hat w_i| \le \frac{s}{2}
\end{gathered}
$$

When values aren't centred on zero (activations after a ReLU live in $[0, \infty)$), **affine** quantisation adds an integer **zero point** $z$: $\hat w = s\,(q - z)$, so the grid covers exactly $[\min, \max]$. This is the scheme Jacob et al. use, with the convenient property that the real number 0 is represented exactly.

Rounding errors don't vanish in a layer: an output $y = \sum_i w_i x_i$ picks up the error $\sum_i (\hat w_i - w_i)\, x_i$. If the errors were independent and uniform on $[-s/2, s/2]$, each would have variance $s^2/12$ and the output error would grow like $\sqrt{n}$ over $n$ inputs. That's why the weights paired with **large** inputs matter most, an idea AWQ builds on.

</Deeper>

## The outlier problem 💥

Now try a nastier group of weights: **0.1, −0.2, 0.15, 10**.

🤔 Predict before you read on: what happens to the three small weights at 4 bits?

The scale must stretch to fit the 10: 10 ÷ 7 ≈ 1.43. Divide the small weights by 1.43 and you get 0.07, −0.14 and 0.1. **All three round to 0.** One outlier has wiped out its neighbours.

This isn't a made-up worry. Large transformers develop a few **outlier features**: hidden dimensions whose values are far bigger than the rest. Quantise them naively with everything else and quality collapses.

---

## Taming the outliers

Researchers found several fixes, and real methods combine them:

- **Smaller groups.** Give every block of, say, 32 or 128 weights its own scale, so one outlier only hurts its own block. Storing the extra scales costs a little: 4-bit weights with one 8-bit scale per 32 weights average **4.25 bits**.
- **Keep outliers in high precision.** LLM.int8() (2022) multiplies the rare outlier dimensions in 16-bit and everything else in 8-bit, more than 99.9% of the values. It reported no loss in quality, even for 175-billion-parameter models.
- **Protect what matters.** AWQ (2023) noticed that protecting about 1% of **salient** weights, chosen by the size of the activations they meet, greatly reduces the error.
- **Round smarter.** GPTQ (2022) quantises weights one at a time and nudges the not-yet-quantised ones to cancel the error so far. It reached 3–4 bits per weight with little accuracy loss, quantising a 175-billion-parameter model in about four GPU hours.

---

## Recipes in practice

**When** you quantise matters:

- **Post-training quantisation (PTQ):** take a finished model and quantise it, using a small **calibration** set of example inputs to choose the scales. Quick and cheap; GPTQ and AWQ work this way.
- **Quantisation-aware training (QAT):** simulate the rounding during training, so the model learns weights that survive it. More work, usually more accurate at low bit-widths.

And **what** you quantise: the **weights** only (the most common for running models on your own machine), the **activations** too (so the arithmetic itself runs in low precision), or the **KV cache** for long contexts.

Newer hardware also computes directly with tiny **floating-point** formats such as FP8 and FP4, where each block of numbers shares a scale. A concrete example: when OpenAI released its open-weight gpt-oss models in August 2025, the mixture-of-experts weights (over 90% of all parameters) were stored in the MXFP4 format at about 4.25 bits per parameter, which let the 120-billion-parameter model fit on a single 80 GB GPU.

## Common misconceptions

- **"A quantised model is a different, smaller model."** It's the same model with coarser numbers. Making a genuinely smaller model is distillation (the distillation lesson covers it).
- **"Quantisation is free."** 8-bit is often nearly lossless and good 4-bit methods come close, but every bit you remove costs some accuracy, and going lower gets harder and harder. Always evaluate on your own task.
- **"Fewer bits are always faster."** Only if the hardware and software support them. Otherwise the numbers are unpacked back to 16-bit on the fly: you still save memory and bandwidth, but not arithmetic.
- **"It's only for inference."** Mostly, but QLoRA fine-tunes adapters on top of a 4-bit frozen model (the LoRA lesson covers this), and low-precision training is an active area.

## What you learned

- Weight memory is **weights × bytes per weight**; going from 16 to 4 bits cuts it by 4×.
- Fewer bytes also means **faster generation**, because moving weights is the bottleneck.
- Quantisation picks a **scale**, rounds to a small integer grid, and multiplies back; each weight moves at most half a step.
- **Outliers** stretch the grid and wreck their neighbours, so real methods use **small groups**, keep outliers in high precision, or **round smarter**.
